# Autonomous 5G Modem Bring-Up on Galaxy S23 (SM8550) Under Windows 11 ARM64: Master Engineering Truth and Multi-Agent Coordination Blueprint
Getting 5G cellular working on a Samsung Galaxy S23 (`dm1q`, Qualcomm Snapdragon 8 Gen 2 / SM8550) running native Windows 11 ARM64 through fully autonomous frontier AI agents (as of November 22, 2026) is **realistically achievable for 5G NSA/SA network registration, SIM/eSIM management, SMS, and real IPv4/IPv6 mobile broadband data, but not realistically achievable end-to-end for carrier VoLTE/VoNR voice calls or certified emergency telephony**. No official Qualcomm Windows 11 Board Support Package (BSP) exists for SM8550 or its IoT variants `QCS8550` and `QCM8550`, and no public Windows-on-ARM smartphone port has demonstrated working integrated cellular on any Snapdragon 8 Gen 2 device. Directing AI agents to transplant closed-source Qualcomm Windows `.sys` drivers from unrelated Snapdragon generations will trap them in opaque ACPI boot-order deadlocks and incompatible hardware register maps.
The viable engineering strategy—and the blueprint designed to coordinate your agent swarm—is a **clean-room hybrid stack**: thin, custom ARM64 Windows KMDF kernel drivers handling hardware transport (TrustZone SCM/PAS boot, SMEM, IPCC, SMP2P, GLINK, IPA v5.5 / GSI v5.0 rings, and `NetAdapterCx`/`MBBCx`) paired with a sandboxed Windows userspace service (`s23modemd.exe`) handling QRTR routing, QMI messaging, RAM-backed `rmtfs`, `pd-mapper`, `tqftpserv`, and eventually an MBIMEx 3.0 translator. Unlike proprietary Windows `.sys` binaries, every SM8550 hardware protocol required for MPSS boot and IPA v5.5 data transport is documented in upstream Linux mainline and open clean-room references, making it fully legible to frontier coding models. Furthermore, your existing repository (`mahanytt/s23-windows-11`, commit `ea78aa952ff3f93f1e096132781cbadf8c89d00d`) already contains a proven WSL-to-Windows ARM64 driver build/sign workflow, remote control tooling (`s23link.py`), draft modem ASL tables, and a 49.2 KB `s23pilprobe.c` driver.
Two strict constraints govern how your agents must execute from this document. First, while the 137-entry directory structure and file sizes of `mahanytt/s23-windows-11` were audited here, the internal source contents of `HANDOFF.md`, `modem_5g_research/`, and `s23pilprobe.c` were inaccessible during research; Milestone M0 therefore mandates a local ground-truth audit before writing new code. Second, **unattended agent operations on live smartphone storage carry permanent bricking risk to your Galaxy S23's IMEI and RF calibration partitions (`modemst1`, `modemst2`, `fsg`, `fsc`, `efs`, `sec_efs`)**. Safety barriers—immutable off-device backups, RAM-only `rmtfs` sandboxing, and hard-coded write blocklists—must live in deterministic Python harness code rather than LLM prompts, paired with a read-only Evaluator Agent enforcing a Default-FAIL hardware verification ladder.

## The Tough Truth: Ecosystem Reality and Why Porting Qualcomm Windows Drivers Fails
As of November 22, 2026, Microsoft's officially supported Qualcomm processor list for Windows 11 IoT Enterprise (LTSC 2024, version 24H2, and version 25H2; last updated June 24, 2026) covers Qualcomm Dragonwing `QCS6490`, `QCM6490`, `QCS5430`, `QCM5430`, `IQ-X7181`, and `IQ-X5121`, alongside Snapdragon `8cx`, `8c`, `7c`, and `850` PC processors. Neither `SM8550` nor `QCS8550` / `QCM8550` appears on that list; commercial QCS8550 modules such as the Lantronix Open-Q 8550CS ship exclusively with Android and Qualcomm Linux / Yocto. Meanwhile, commercial 5G Windows PCs built on platforms such as Snapdragon X Elite rely on discrete or M.2 5G Modem-RF systems (such as Snapdragon X55, X62, or X65), and Microsoft's inbox Mobile Broadband Class Driver (`MBCD`) and `MBBCx` stack assume an MBIM-speaking MBB adapter rather than an integrated SM8550 Hexagon MPSS communicating over SMEM, GLINK, and IPA.
Community Windows-on-ARM smartphone ports reinforce this divide cleanly. Project Renegade's support matrix confirms working cellular data on `SDM845` (adjacent to Windows-native `SDM850` laptop BSPs) and on 4G-only `SM8150` devices such as the OnePlus 7 Pro 4G and 7T Pro 4G—while leaving the 5G `SM8150` LG V50, `SM8250` (Snapdragon 865), and `SM8350` (Snapdragon 888) unsupported for both data and calls. DuoWOA achieved working LTE data, eSIM, SMS, and manually provisioned calls on Surface Duo 1st Gen (`SM8150`), yet still flags VoLTE as untested due to missing software and warns that Windows provides no emergency calling (later DuoWOA releases added basic speaker and earpiece audio for calls on Duo 1st Gen). By contrast, Surface Duo 2 (`SM8350`, 5G)—despite preview introduction of a Modem Processor Subsystem driver and UEFI PCIe bring-up—remains labeled `"Expert users only, extremely early and rough, not usable at all"` with no usable cellular stack. On SM8550 specifically, the most advanced public Windows 11 handset port (`kevinshroff/oneplus-open-windows`) reports Cellular at **0/3 complete** (zero modem/SIM integration, zero registration, zero data or calls).
Understanding *why* closed-source Qualcomm Windows `.sys` drivers from other Snapdragon chips (such as `QCM6490`, `SC7180`, or Snapdragon 8cx/X platforms) fail on SM8550 prevents your agents from burning massive token budgets on a dead end. First, Qualcomm's IP Accelerator (IPA) hardware breaks binary compatibility across SoC generations: Linux mainline's `ipa_match` table maps `SC7180` to IPA v4.2, `SM8350` to IPA v4.9, `SC7280` to IPA v4.11, `SDX65` to IPA v5.0, and `SM8550` to **IPA v5.5** with **GSI v5.0** register maps, 25 local SMEM regions, and unique endpoint/channel assignments. A proprietary `qcipa` driver compiled for an older IPA generation will write mismatched MMIO registers or hang on invalid GSI doorbells.
Second, `SM8550` uses a **split DTB-first PAS boot sequence**: unlike older Snapdragon SoCs that authenticated a single `modem.mdt` image (`pas_id = 4`), SM8550 requires TrustZone Peripheral Authentication Service (PAS) initialization and reset of a separate modem Device Tree Blob (`modem_dtb.mdt`, `dtb_pas_id = 0x26`) *before* authenticating and starting `modem.mdt` (`pas_id = 4`), paired with explicit memory protection handoffs to `QCOM_SCM_VMID_MSS_MSA` (`0xF`). Third, proprietary Qualcomm Windows BSP stacks exhibit fragile ACPI and boot-order deadlocks across `SPMI → GPIO → PMIC → PIL → Subsystem`—documented in real-world `SC7180` and Snapdragon X Windows 11 debugging—where missing undocumented ACPI `_HID`/DSM methods or wrong service `Start` orders trigger `CM_PROB_FAILED_DRIVER_ENTRY` or stall subsystems indefinitely. An autonomous coding agent cannot inspect or patch closed-source Qualcomm `.sys` internals to break an SM8550 deadlock, whereas it can instrument, trace, and verify every line of a clean-room driver derived from upstream Linux SM8550 source.

## Target Architecture: Clean-Room Hybrid Kernel and Userspace 5G Stack
To maximize autonomous agent throughput while minimizing Windows kernel BSOD reboot cycles, enforce a **clean-room transport-versus-protocol split** modeled on non-Linux Qualcomm telephony bring-ups—specifically the `NeoSymbian` clean-room architecture, which isolated SCM, SMEM, SMP2P, GLINK, remote-processor boot, and IPA rings in kernel space while executing QRTR, QMI, `rmtfs`, `pd-mapper`, and `tqftpserv` in a single userspace Rust process to bring up ~40 QMI services and LTE IPA packet data. Adapting that architecture to Windows 11 ARM64 cleanly separates two thin KMDF kernel drivers from a fast-iterating userspace daemon (`s23modemd.exe`).
Moving QRTR routing, QMI TLV encoding/decoding, `rmtfs`, `pd-mapper`, `tqftpserv`, and modem state machines out of the kernel into a standard Win32/Rust userspace service (`s23modemd.exe`)—bridged to `s23modem_xprt.sys` through four narrow IOCTLs (`IOCTL_PIL_BOOT_SHUTDOWN`, `IOCTL_GLINK_TX_RX`, `IOCTL_SMEM_READ_ITEM`, and `IOCTL_RMTFS_MAP_CARVEOUT`)—solves two major bottlenecks for autonomous AI work. First, any malformed QMI TLV packet, parser edge case, or unexpected modem indication crashes only `s23modemd.exe` with an immediate stack trace instead of bugchecking the Windows ARM64 kernel and forcing a full phone reboot. Second, it unlocks true parallel development: the Userspace Builder Agent can implement and fuzz-test the entire QRTR/QMI/`rmtfs`/`pd-mapper`/`tqftpserv` engine off-device against synthetic frames while the Kernel Builder Agent works exclusively on SM8550 silicon bring-up.
To further de-risk Windows networking integration, deliver the IPA data driver (`s23ipa_net.sys`) in two decoupled phases rather than coupling raw DMA debugging to MBIM state-machine complexity. In **Phase A (Raw IP via `NetAdapterCx`)**, implement `s23ipa_net.sys` as a minimal `NetAdapterCx` miniport advertising `*MediaType = 19` (`NdisMediumIP`, raw IP frames without Ethernet headers). Driver-developer reports on OSR NTDEV indicate that `NetAdapterCx` binds cleanly to Windows 11 `tcpip.sys` under `NdisMediumIP`, whereas `NdisMedium802_3` fails IPv4 binding unless `NetAdapterSetReceiveFilterCapabilities` is explicitly implemented and NetAdapterCx v2.2+ (WDK 10.0.22621+) targets Windows 11 specifically. During Phase A, `s23modemd.exe` invokes QMI `WDS Start Network`, retrieves the assigned IPv4/IPv6 address, gateway, and DNS via QMI `WDS Get Current Settings`, and configures the Windows interface directly—delivering live 5G internet and throughput validation before writing a single line of MBIM translation.
In **Phase B (Native Windows 11 5G UI via `MBBCx` + `MBIMEx 3.0`)**, once IPA v5.5 ring transfers are proven stable, layer Microsoft's Mobile Broadband WDF Class Extension (`MBBCx`) onto the `NetAdapterCx` adapter using `MbbAdapterInitialize`, `EvtMbbDeviceSendMbimFragment`, and `MbbRequestComplete`. Windows `WwanSvc` issues WWAN OIDs down through `NDISUIO` → `NDIS` → `MBBCx` as MBIM control fragments, which your driver proxies to `s23modemd.exe` for translation into QMI (`DMS`, `UIM`, `NAS`, `WDS`, `WMS`). Target **MBIMEx 3.0 (5G SA Phase 1 + 5G NSA parity)**, which Windows 11 announces by default; skip MBIMEx 4.0 URSP/multi-slice extensions, as Microsoft officially placed MBIMEx 4.0 release on hold (confirmed in Microsoft Learn documentation updated May 24, 2025).

### A. Windows ARM64 Execution Environment and TrustZone SCM/PAS Boot
Before loading test-signed custom drivers or executing EL1-to-EL3 Qualcomm TrustZone `SMC` calls, ensure the S23 boots Windows 11 **without the Windows hypervisor or Virtualization-Based Security (VBS/HVCI)** active. When VBS is enabled on ARM64, the Windows hypervisor runs in EL2 with Virtualization Host Extensions (`HCR_EL2.E2H`), enforcing VTL1 code integrity (HVCI) that blocks incompatible or non-WHQL drivers and interposes EL2 virtualization between the NT kernel and TrustZone. Verify in BCD and WMI that `hypervisorlaunchtype off`, `vsmlaunchtype off`, `testsigning on`, and `Win32_DeviceGuard.VirtualizationBasedSecurityStatus == 0`.

Follow upstream Linux's `qcom_pas_start()` ordering strictly when booting MPSS:

1. Prepare base state, enable proxy power domains (`cx` and `mss`), enable `xo` and `aggre2` clocks, enable configured supply regulators (`cx_supply`/`px_supply`), and issue any required AOP QMP load-state vote (`load_state = "modem"`).
2. Execute `QCOM_SCM_MP_ASSIGN` to assign the modem's `mpss_dsm_mem` region to `QCOM_SCM_VMID_MSS_MSA` (`0xF`) and configure shared `HLOS + MSS_MSA` access on `rmtfs_mem` (verifying `qcom,vmid` and 4 KiB guard-page rules from your live `dm1q` DTB, as established in Qualcomm SDM670/SDM845/SM8150 bring-ups).
3. Authenticate and reset the **modem DTB image first**: map its carve-out, call `PAS_INIT_IMAGE(0x26)` → `PAS_MEM_SETUP(0x26, dtb_phys, dtb_size)` → load ELF segments → flush caches → `PAS_AUTH_AND_RESET(0x26)`.
4. Authenticate and reset the **main MPSS image**: call `PAS_INIT_IMAGE(4)` → `PAS_MEM_SETUP(4, mpss_phys, mpss_size)` → load all ELF segments of `modem.mbn` into `mpss_mem` → flush caches → `PAS_AUTH_AND_RESET(4)`.
5. Wait up to 5 seconds for the modem's SMP2P `ready` signal, then monitor SMP2P `handover`—noting from `NeoSymbian`'s bare-metal bring-up that handover can arrive ~0.55 s *after* ready—and release proxy votes promptly upon handover while freeing temporary metadata allocations.

### B. Reserved Carve-Outs, SMEM Forensics, GLINK/QRTR, and Mandatory Daemons
Every modem and DSP carve-out must be excluded from the Windows RAM map inside UEFI (`EfiReservedMemoryType` / `MEM_RES` / `no-map`). If Windows allocates even a single kernel page overlapping `mpss_mem`, `mpss_dsm_mem`, or `rmtfs_mem`, locking that range to `VMID_MSS_MSA` triggers an instantaneous TrustZone XPU fault and hard SoC reset upon the next CPU access. Because Samsung adjusts reserved-memory boundaries across models and bootloader revisions (for example, Galaxy S23 `dm1q` Bit A / SW REV A firmware), your Initializer Agent must extract exact `dm1q` base addresses and sizes from the phone's live Android DTB during M0. As a structural sizing reference, the sibling Samsung SM8550 mainline device tree (`sm8550-samsung-q5q.dts`, Galaxy Z Fold5) plus SM8550 SMEM references (`0x81d00000`, 2.0 MiB—though some SM8550 tables place SMEM at `0x80900000` or elsewhere, reinforcing live DTB verification) total ~472.2 MiB of reserved carve-outs, of which 307.5 MiB are modem-critical, shown alongside the exact SM8550 IPA v5.5 endpoint map below.
Immediately after MPSS clears TrustZone reset, `s23modem_xprt.sys` must parse Qualcomm **SMEM** and bring up **IPCC + GLINK** so `s23modemd.exe` can register the QRTR nameserver and answer modem requests promptly. In `smem.c`, the partition table (`struct smem_ptable`) sits 4 KiB from the end of `smem_mem`, identified by `SMEM_PTABLE_MAGIC` (`$TOC`, `{0x24, 0x54, 0x4f, 0x43}`). Each private partition begins with `SMEM_PART_MAGIC` (`$PRT`, `{0x24, 0x50, 0x52, 0x54}`), and uncached private entries carry canary `0xa5a5`, `item`, `size`, `padding_data`, and `padding_hdr` (stepping via `Current + sizeof(hdr) + padding_hdr + size`). Building an SMEM lookup helper first pays immediate dividends: item `421` (`SMEM_SSR_REASON_MSS0`) exposes the modem's exact Hexagon panic string whenever MPSS crashes, turning blind failures into actionable diagnostics.
GLINK native SMEM transport locates its descriptors and ring buffers in SMEM items `478` (`XPRT_DESCRIPTOR`), `479` (`FIFO_0`), and `480` (`FIFO_1`), signaled over SM8550 IPCC doorbells (`qcom,sm8550-ipcc`). Following the `GLINK_CMD_VERSION` (`0`) / `VERSION_ACK` (`1`) handshake, MPSS opens `IPCRTR`, `glink_ssr`, and `SSM_RTR_MODEM_APPS`. Once `s23modemd.exe` (QRTR Node 1) broadcasts `HELLO` over `IPCRTR`, the modem (Node 0) responds with `NEW_SERVER` (type 4) packets advertising roughly 40 QMI services. As documented in `NeoSymbian`'s Qualcomm bring-up, if the AP fails to answer the modem's `rmtfs` or `tqftpserv` requests, MPSS raises a fatal crash signal (SMP2P bit 0) roughly 60 seconds after reaching ready; all three AP-hosted services below must therefore be active before launching MPSS:

| Service | QMI / QRTR ID | Version / Instance | Required Behavior & Critical Pitfalls |
| --- | --- | --- | --- |
| **`rmtfs` (Remote Filesystem)** | QMI `14` | Standard | Serves `modemst1` (`/boot/modem_fs1`), `modemst2` (`fs2`), `fsg`, and `fsc` through `rmtfs_mem`. **Pitfall (`NeoSymbian`):** in `rw_iovec`, `phys_offset` is an **absolute physical RAM address**, not a buffer-relative offset—misinterpreting it breaks EFS reads/writes. ### C. IPA v5.5 / GSI v5.0 Data Plane and the ARM64 Windows DMA Coherency Trap
Bringing up 5G packet data on SM8550 means implementing the **IP Accelerator (IPA v5.5)** and **Generic Software Interface (GSI v5.0)** driver following Linux mainline's 3-stage initialization (`Init` → `Config` at 120 MHz core clock with `memory` 1.9 GB/s peak / `config` 76.8 MB/s peak interconnect votes → `Setup`). Note a crucial SM8550 clock-tree dependency patched upstream in 2026: SM8550 GCC GDSCs require holding the parent **RPMh `CX` power domain vote**, without which IPA register accesses can hang silently. Four specific traps must be codified into your Kernel Builder Agent's skills before it writes `s23ipa_net.sys`.
**Verify `qcom,gsi-loader` Mode in `dm1q` DTB Before Coding the Loader.** Upstream `ipa_main.c` supports AP-loaded GSI firmware (`IPA_LOADER_SELF`, loading `ipa_fws.mdt` via TrustZone `IPA_PAS_ID = 15`), modem-loaded firmware (`IPA_LOADER_MODEM`, waiting on the modem's SMP2P `setup-ready` interrupt before invoking `ipa_setup()`), or `skip`. Because exact SM8550 `ipa` MMIO register bases, GIC SPI IRQ numbers, and `qcom,gsi-loader` values depend on the board DTS, your M0 audit must extract them verbatim from upstream `sm8550.dtsi` and your live `dm1q` DTB rather than guessing.
**Complete the Exact 4-Step QMI `0x31` Handshake Before Arming Data Rings.** During `ipa_setup()`, initialize GSI (`gsi_setup`), enable `AP_COMMAND_TX` (Ch 12 / EP 14), initialize all 25 local IPA SMEM regions (`0x0000`–`0x4ee8` within the 44 KiB SMEM block, writing the required 2-canary guards specified by `ipa_data_v5_5`), set up filter/route tables, enable `AP_LAN_RX` (Ch 13 / EP 16) as default exception route, and start the QMI `0x31` server (instance `1`) and client lookup (instance `2`). On initial boot, AP transmits `IPA_QMI_INIT_DRIVER`, waits for both the modem's response (`modem_ready`) and the modem's `IPA_QMI_DRIVER_INIT_COMPLETE` request (`uc_ready`, sent after MPSS loads the IPA microcontroller), acknowledges `IPA_QMI_INDICATION_REGISTER`, and sends `IPA_QMI_INIT_COMPLETE` before enabling `AP_MODEM_TX` (Ch 11 / EP 2) and `AP_MODEM_RX` (Ch 1 / EP 23). On subsequent modem restarts (SSR), `uc_ready` remains true and AP sets `skip_uc_load = 1`.
**Eliminate the ARM64 Windows DMA Cache Coherency (`_CCA`) Trap.** This is the single highest-probability silent failure on SM8550 Windows ports—in fact, `oneplus-open-windows` (SM8550) identified effective cache attributes of DMA ring/common buffers as the leading suspect in its Wi-Fi firmware credit stall. Upstream Linux explicitly marks the SM8550 APPS SMMU as **`dma-coherent`**. On ARM64 Windows, however, Microsoft's `AllocateCommonBuffer` **ignores the driver's `CacheEnabled` parameter and obeys the device's ACPI `_CCA` method instead**. If your ACPI DSDT entry for IPA omits `Name (_CCA, 1)`, Windows maps uncached common buffers as **ARM Device Memory**, where any unaligned CPU memory access raises an immediate hardware alignment fault (BSOD) and standard kernel routines reject the buffer. Always declare `_CCA = 1` on cache-coherent SM8550 DMA devices in ACPI, verify SMMU stream-ID mapping/bypass, and set `WDF_DMA_ENABLER_CONFIG.WdmDmaVersionOverride = 3` when creating the `WDFDMAENABLER` for `NetAdapterCx`.
**Implement QMAPv5 Framing, Checksum Offload, and Headroom Accurately.** On SM8550, both `AP_MODEM_TX` and `AP_MODEM_RX` enable `qmap = true` and `checksum = true`, with 8192-byte RX aggregation buffers and a 500 µs aggregation timer. Configure the modem via QMI `WDA Set Data Format` for the embedded endpoint type and QMAPv5 aggregation. Ensure egress framing reserves headroom for both the QMAP header and the 4-byte `struct rmnet_map_v5_csum_header` (`header_info`, `csum_info`, `__be16 reserved`)—an exact MTU/headroom oversight that required an upstream Linux `rmnet` patch on November 17, 2026.
